Image-Level PHI Redaction (Item 1)

### 3.1 The privacy problemWhen a user captures a photo for NutriVision, the photo may incidentally contain non-food content: the user's face reflected in cutlery, prescription medication bottles on the table, the user's child in the background, household interior identifying the user's location, hand tattoos, etc. The standard Anthropic Vision API privacy posture is appropriate (the provider does not retain photos beyond the analysis call and does not perform facial recognition), but the user has not consented to that content being analyzed at all. The content is incidental, not intentional.170c §3 implements image-level PHI redaction: an on-device segmentation pass that identifies food regions and applies Gaussian blur to non-food regions before the photo is transmitted to the vision provider.

### 3.2 The technical approachThe redaction pipeline:Capture. User takes a photo via the standard 170 capture flow.On-device inference. A lightweight food segmentation model runs on-device, producing a binary mask: food pixels vs non-food pixels.Blur application. Non-food regions of the photo are blurred with a Gaussian kernel (sigma 12 to 18 depending on image resolution).Transmission. The redacted photo (food regions clear, non-food regions blurred) is sent to the vision provider.Standard analysis. The vision provider analyzes the redacted photo. The food regions are unblurred and fully analyzable; the blurred regions contain insufficient detail for the provider to extract meaningful non-food information.

### 3.3 The segmentation modelModel requirements:Size under 10 MB to bundle in the mobile app without unacceptable bundle bloat.Inference latency under 300 ms on a mid-range device (target: iPhone 12 / Samsung Galaxy A52 class).Mean IoU above 0.75 on a Gordon-curated food segmentation test set of 200 images.Quantized to INT8 for on-device performance.Candidate architectures for Blueprint evaluation:MobileNetV3 + DeepLabV3 head fine-tuned on food segmentation datasets. Open-source food segmentation work in the academic literature provides starting points.EfficientNet-Lite + custom segmentation head with food-specific fine-tuning.Pre-trained food segmentation models from academic groups (UEC FOOD, Food-101 segmentation extensions).Gordon and engineering jointly evaluate candidates during Blueprint. The model choice is a Blueprint deliverable.

### 3.4 The Capacitor pluginOn-device inference requires platform-native runtime: TensorFlow Lite on Android, Core ML on iOS, or ONNX runtime as a cross-platform alternative.Capacitor plugin candidates for Blueprint evaluation:@capacitor-community/tflite-react-native@capacitor-community/onnxruntime (when available; community maintenance status varies)Custom-built Capacitor plugin wrapping platform-native ML runtimes.The selection is a Blueprint deliverable with security review of the plugin internals.

### 3.5 The fallback behaviorInference can fail: the model fails to load (corrupted bundle), inference times out (slow device), the model produces an unreasonable mask (all food or all non-food), or platform-level errors occur.When inference fails:The photo is sent unredacted to the vision provider.A flag phi_redaction_applied = false is set on the nutrition_photo_jobs row.A telemetry event phi_redaction_failed fires.The user is not notified at capture time (would create user-visible noise for an internal infrastructure issue).The aggregate failure rate is monitored via the cost dashboard (Section 9).The fallback is honest: redaction is best-effort, not guaranteed. Section 3.7 documents the residual risk.

### 3.6 Performance budgetThe full redaction pipeline must fit within 500 ms total on a mid-range device (300 ms inference + 200 ms blur application + transmission overhead):Inference: under 300 ms.Mask resize to original photo resolution: under 50 ms.Gaussian blur application (Android RenderScript, iOS Core Image, or Capacitor cross-platform image processing): under 100 ms.Total: under 500 ms.If the pipeline exceeds this budget on a specific device:The pipeline aborts.Fallback (no redaction) applies.Telemetry records the device characteristics for future model optimization.

### 3.7 Residual risk acknowledgmentEven with successful redaction, residual risk remains:The model is not perfect; some non-food regions may be classified as food.Food regions may incidentally include identifiable hands, jewelry, or other personal markers.The vision provider's full analysis of food regions includes interpreting the image, which is appropriate for nutrition analysis but not zero-information about the user.170c §3 reduces but does not eliminate the privacy risk of capturing photos. The fundamental privacy is the user's choice: photos contain whatever the user includes when they frame the shot. 170c is best-effort technical reduction within that constraint.

### 3.8 PHI redaction in the photo capture UXThe user does not see the redaction happen. The UX is silent and the redacted image is not surfaced to the user:Capture occurs the standard way.Inference and blur run silently in the 500 ms processing window.The result review screen shows the original (unredacted) photo to the user: the user's privacy reduction happens for the vision provider only; the user can see what they actually captured.Settings > Privacy includes a description of the redaction with a "Learn more" link to a Kelsey-authored explainer.The silent UX matches the user expectation: the user does not need to act, see, or understand the redaction for it to provide privacy benefit.

### 4.1 The three rightsGDPR Articles 15, 17, and 20 (and equivalent provisions in CCPA, PIPEDA, and other regulations) give users:Right to access (Article 15): the user can request a copy of their personal data.Right to erasure (Article 17): the user can request deletion of their personal data.Right to data portability (Article 20): the user can receive their personal data in a structured, machine-readable format.170c §4 implements all three rights specifically for the user_meal_corpus table. (Other domains: CAQ, supplement protocols, GENEX360 results: have their own DSAR implementations in their respective prompts.)

### 4.2 The user_hash registry problemThe user_meal_corpus table from Prompt 170g stores corpus rows keyed by user_hash, where user_hash is a salted hash of the user_id. The salt rotates periodically (post-launch policy: every 90 days) to limit cross-time correlation. Each rotation creates a new salt_version.This creates a DSAR challenge: when a user requests their data or requests erasure, the system needs to enumerate every hash the user has ever had across all salt_versions. Without a registry, the only way to find a user's corpus rows is to brute-force across all rotations: infeasible.The solution: a corpus_user_hash_registry table that records every (user_id, user_hash, salt_version) tuple created.sql-- supabase/migrations/20260601_corpus_user_hash_registry.sqlCREATE TABLE IF NOT EXISTS public.corpus_user_hash_registry (  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,  user_hash TEXT NOT NULL,  salt_version INT NOT NULL,  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),  retired_at TIMESTAMPTZ);CREATE UNIQUE INDEX IF NOT EXISTS idx_corpus_user_hash_registry_unique  ON public.corpus_user_hash_registry(user_id, salt_version);CREATE INDEX IF NOT EXISTS idx_corpus_user_hash_registry_hash  ON public.corpus_user_hash_registry(user_hash);-- Service role only; user_id is sensitive in this table since it links back to user.ALTER TABLE public.corpus_user_hash_registry ENABLE ROW LEVEL SECURITY;-- No user-facing policies. Access only via service-role functions.The registry itself is sensitive: it links pseudonymized user_hash values back to user_id, breaking the pseudonymization. Access is service-role only; the table is not queryable from user-facing APIs.

### 4.3 Right to access implementationThe user accesses Settings > Privacy > Download my nutrition data. Tapping triggers:The system enumerates all (user_hash, salt_version) tuples for the user_id from corpus_user_hash_registry.The system queries user_meal_corpus for rows matching any of those hashes.The system assembles a JSON archive with the structured corpus data.The archive is uploaded to a time-limited signed URL (24-hour expiration).The user receives an email and in-app notification: "Your data export is ready. The download link expires in 24 hours."JSON archive structure:json{  "schema_version": 1,  "exported_at": "2026-06-30T12:00:00Z",  "user_id_pseudonymized": "user_export_token_abc",  "corpus_rows": [    {      "row_id": "corpus_001",      "captured_at": "2026-04-15T19:43:00Z",      "schema_version": 1,      "salt_version_at_creation": 3,      "meal_items": [...],      "estimated_macros": {...},      "data_source": "photo_capture",      "confidence_at_save": 0.84    }  ],  "metadata": {    "total_rows": 142,    "earliest_row": "2026-04-01",    "latest_row": "2026-06-29"  }}The archive is human-readable JSON. Machine-readable for users wanting to import into other systems.

### 4.4 Right to erasure implementationThe user accesses Settings > Account > Delete my account. Account deletion triggers a multi-step flow:Confirmation. User confirms with password re-entry.Grace period. Account enters a 30-day grace period in which deletion can be reversed. During grace period the user retains full account access.Final confirmation at grace period end. User receives an email at 23-day mark: "Your account will be permanently deleted in 7 days. Tap here to cancel."Hard deletion. At grace period end, the account is hard-deleted.Hard deletion of user_meal_corpus rows:Enumerate all (user_hash, salt_version) tuples for the user_id from corpus_user_hash_registry.Delete corpus rows matching any of those hashes.Delete the registry rows themselves.Delete the user's auth.users row.Delete all other user data (handled by other prompts' DSAR implementations).Log the deletion event in audit_account_deletions with timestamp, deletion_token (for legal compliance audit), and a count of corpus rows deleted.

### 4.5 Right to data portabilityPortability is satisfied by the right-to-access JSON export. The format is:Structured JSON (machine-readable).Documented schema with schema_version field for forward compatibility.Includes all corpus rows belonging to the user.Does NOT include data that originates from other users or aggregate statistics.A user could (in principle) import this archive into another nutrition tracking system that supports import. ViaConnect provides the data; the receiving system is responsible for import compatibility.

### 5.1 The user-facing problemA user with declared dairy sensitivity in CAQ Phase 6 logs a meal via photo capture. The vision provider identifies cheese, milk, or butter in the meal. ### 5.2 The supported restrictionsCAQ Phase 6 captures both allergens and dietary patterns:Allergens (per Prompts 15 through 17):GlutenDairyTree nuts (almonds, cashews, walnuts, etc.)PeanutsShellfishSoyEggsSesameFish (separately from shellfish)SulfitesDietary patterns:Keto / low-carbVeganVegetarianLacto-vegetarianPescatarianHalalKosherGluten-free (separate from gluten allergen; some users follow without allergen)Each allergen and pattern has a Gordon-curated detection ruleset: a list of food categories, ingredient strings, and cascade-name patterns that indicate the restriction is violated.

### 5.3 The detection algorithmFor each meal_items row in a parsed meal, the system:Looks up the canonical food category and ingredient list from the cascade.For each user-declared restriction, checks if any ingredient or category triggers the restriction's ruleset.If a trigger fires, generates a dietary_restriction_conflict entry with severity (high for allergens, medium for patterns).The result review screen surfaces the conflicts inline.

### 5.4 The UX surfaceOn the NutriVision result screen, conflicts surface as:An inline banner above the meal_items section: "Heads up: this meal contains {restriction}. You marked yourself as {restriction-sensitive / following X pattern} in your health profile."The specific meal_items triggering the conflict are highlighted with an amber border and a small allergy icon (Lucide AlertCircle).A "Why am I seeing this?" link expands to Kelsey-authored explanation of where the user declared the restriction and how to update it in CAQ.The framing is informational, not prescriptive:High severity (allergens): "This meal contains dairy. You marked yourself as dairy-sensitive in your health profile."Medium severity (patterns): "This meal includes meat. You follow a vegetarian pattern in your health profile."No "you should not eat this" language. The user has agency; the system informs.

### 5.5 The "this conflict is incorrect" affordanceThe cascade and vision provider are not infallible. A user may see a flagged conflict that is actually wrong (the system thinks the meal contains shellfish but it actually contains chicken). The user can mark the conflict as incorrect:The conflict banner has a "Not actually present" dismiss affordance.Dismissing the conflict adjusts the meal_items (removes the misidentified ingredient).Telemetry logs the correction for ingredient detection improvement.
